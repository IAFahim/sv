# sv in Unity 7

Unity 7000.0.0a16 (newest editor only), Entities 7.0.0, Collections 7.0.0, Burst 2.0.0. sv does not reference tl or Unity; the Unity adapter and the tl glue live in the host.

## Packages

| Package | What it is |
|---|---|
| `com.sv.engine` | `Sv.Core`, `Sv.Host` (runtime) and `Sv.Rules` (editor only) copied verbatim from `src` by `eng/engine-sync.sh sync` (`check` fails on drift) |
| `com.sv.unity.v4` | the adapter: generated Burst jobs per frame phase, `SvWorld`, `SvStepSystem` and the fixed-step systems, `SvSlot`, `SvOutboxSystem<T>`, reload hook, pack authoring window; `Sv.Unity.V4.Tl` (only with `com.tl.unity`): `SvTimelineRequestSystem`, `SvTimelineClockSystem` |
| `com.sv.columns` | sv v4: `Sv.Columns` copied verbatim by `eng/columns-sync.sh`, plus `ColumnHost` (MonoBehaviour) and `ColumnStepper` (managed jobs) |
| `com.sv.columns.entities` | sv v4 in Entities and Burst: the frame as two Burst jobs, an `ISystem`, components, bakers and an Arena sample (below) |

## Use

1. Add `com.sv.engine` and `com.sv.unity.v4` to `Packages/manifest.json` as `"file:<sv checkout>/packages/<name>"`.
2. Write the pack (`values`, `rules`, `cards`, `templates` `.sv.json`) with the authoring window (Window > sv > Pack Authoring) or by hand and generate with `sv pack <folder> --host unity --namespace <ns> --out <dir>` or the window's Regenerate. The output is `Values.g.cs`, `Kernels.g.cs`, `HostKernels.g.cs`, `PackData.g.cs`, `PackJobs.g.cs`, `Rules.map.txt`. Put it in a game assembly that references `Sv.Engine.Core`, `Sv.Engine.Host`, `Sv.Unity.V4`, `Unity.Burst`, `Unity.Collections`.
3. `PackWorld.Create(new HostOptions { Workers = ..., Parts = 64 })` returns an `SvWorld<HostKernels>`. `Spawn(template)`, `Send(...)`, `Modify(StatOp)`, `Step()`, `Read(slot, lane)`, `Digest()`.
4. In ECS: `SvEntities.Publish(entityManager, world)` creates the world handle entity, `SvEntities.Attach(entityManager, entity, world, template)` gives an entity a slot, and `SvStepSystem` (in `SimulationSystemGroup`, first) kills the slots of destroyed entities and steps the world. `SvWorlds.DisposeAll()` runs before every assembly reload.

## Proof

`COMPILE_ONLY=1 T=c1 bash m8-run/locked.sh m8-run/gate.sh` then the same without `COMPILE_ONLY` (scripts in `eng/m8-run`, set-up in `docs/M8-HANDOFF.md`). Expect 0 `error CS`, 0 `warning CS`, 0 `error BC` and every EditMode test green. Every generated job carries a probe: 1 means it ran as a Burst job.

## Player builds (Burst AOT; Linux CoreCLR proven, Windows and IL2CPP selectable)

The target follows the OS (`linux64`, or `win64` under Git Bash on Windows; override with `SMOKE_TARGET`) and the backend is `SMOKE_BACKEND=coreclr` (default) or `il2cpp`; the build fails if the backend did not take. The run line also prints `il2cpp=yes|no` (a `GameAssembly` file next to the player). On Windows set `U` to `Unity.exe`, for example `U="/c/Program Files/Unity/Hub/Editor/7000.0.0a16/Editor/Unity.exe" SMOKE_BACKEND=il2cpp bash eng/player-smoke.sh`.

`bash eng/player-smoke.sh` builds a Linux player from a throwaway project (the three test packs as a runtime assembly, the 37 twin journals under StreamingAssets), runs it headless and replays every journal at 1 and 11 job workers: every per-frame digest must equal the .NET host's and every phase must run as Burst (`SvProbe.ManagedRuns` 0). Set `KEEP=1` to keep the project, `U` for another editor. Result on 2026-11-14 (Unity 7000.0.0a16, `LinuxStandaloneSupport` CoreCLR player): build Succeeded, 0 error CS, 0 error BC, `lib_burst_generated.so` present; `SVSMOKE summary cases 74 frames 324 failures 0 maxJobWorkers 11 managedRuns 0`. This editor ships CoreCLR players only (no Mono, no IL2CPP variation installed), so those backends are not covered.

## tl in Unity (plain host, M9 Unity leg)

tl runs inside Unity on its plain host: `TimelineWorld`, `PlaybackTable`, `KindStore` and the generated system over managed column arrays, on the main thread or `TlWorkers`. No SubScene, Timeline asset or ECS system is involved. The worked example is `packages/com.sv.unity.v4/Tests/Tl` (NorthStar3).

1. Import `com.tl.unity` (`"com.tl.unity": "file:<tl.unity checkout>/com.tl.unity"` or its git URL). The plain path uses only its `Tl.Core` assembly, whose sources equal tl's `src/Tl.Core`. Do not list `com.tl.unity` under `testables`: its own test assemblies would register kinds twice. The sv tl leg (`Sv.Unity.V4.TlGenerator`, `Sv.NorthStar3`, `Sv.Unity.V4.TlTests`) compiles only when `com.tl.unity` is in the project (`versionDefines` set `SV_TL_UNITY`) and tests are included, so a project without tl still compiles the rest of `com.sv.unity.v4`.
2. The generator is `Tl.Gen.Plain.dll`, copied from tl.unity's `com.tl.unity/Tests/Plain/Generator` by `eng/tl-plain-sync.sh sync` (`check` compares it with `eng/tl-plain.stamp` and with the tl.unity copy). `sync` also writes the tl.unity commit it copied from (`tl.unity=` in the stamp), and refuses a checkout with uncommitted changes under `com.tl.unity`. `eng/unity-ci.sh` fetches that commit into `~/.cache/sv-tl-unity` and adds `com.tl.unity` to the probe, so the tl leg runs on every Unity CI run; `TL_UNITY_ROOT` points it at another checkout instead. It sits in a folder with its own asmdef (`Tests/Tl/Generator`), and the game assembly references that asmdef, so the analyzer runs on the game assembly only. Its plugin settings are label `RoslynAnalyzer` and no platforms. Set them through Unity, never in the `.meta` by hand: an `-executeMethod` in the scratch project that calls `PluginImporter.SetCompatibleWithAnyPlatform(false)`, `SetCompatibleWithEditor(false)`, `SaveAndReimport()` and `AssetDatabase.SetLabels(dll, new[] { "RoslynAnalyzer" })`. The committed `.meta` carries the result. Unity cannot run that method while a script fails to compile, so do it before adding code that uses the generated system.
3. `Tl.Gen.Plain` runs on any assembly with a timeline declaration (clips, tracks, kinds, states), as tl's .NET generator does (since tl.unity `6d613db`; before it, the glue had to carry an empty `[TimelineSystem]` struct). It emits `Tl.Generated.TlAuto_<AssemblyName>`, the same code tl's .NET generator emits. Since tl `d87d1998` there is no module to install: the host builds the generated struct and calls `Run`.
4. Bake the library with tl's `tlb library` over the timeline JSON, against the compiled game assembly: `dotnet Tl.Bake.dll library Tests/Tl/Glue/Timelines~ --assembly <project>/Library/ScriptAssemblies/Sv.NorthStar3.dll --out Tests/Tl/Glue/game.bytes --no-sources`. The library metadata records the clip type's assembly name, so the Unity glue assembly has the same name as the .NET one (`Sv.NorthStar3`). Then the bytes equal the library the .NET host bakes in code. `tests/Sv.NorthStar3/UnityLegTests.cs` checks three things: the Unity glue equals the emitter output, `game.bytes` equals `Rig.Library()`, and the fixture bakes to the same bytes. `SV_UPDATE_TWIN=1` rewrites the glue and `game.bytes`.
5. Each frame: `NorthStar3Timelines.TickAndFillOutboxes()` (tl `Tick`, then `TlAuto_Sv_NorthStar3.Run` adds the clip amounts to the `[TlState]` outbox columns), then `Outbox.Send(world.Loop, cells, channel, kindLane, targetLane)` per timeline channel (Collect: the cells become `Origin.Timeline` records), then `SvWorld.Step()` (the generated Burst jobs), then `TimelineRequests.Apply` with the frame's events.

Proof: `Sv.Unity.V4.TlTests` replays the five NorthStar3 journals at 1 and 11 job workers. tl writes the outbox, and Collect feeds the SvWorld. Each frame, the cells tl wrote equal the timeline sends the .NET host collected, and every per-frame digest equals the journal's, including the pins `A566FAEC8837BA57` and `2D6A06776AE25DCB`.

## tl and sv in Entities (one clock, Burst glue; issue 0528)

tl.unity ticks in `TlSimulationGroup`, inside `FixedStepSimulationSystemGroup`. sv has two clocks, picked per world handle, and exactly one runs:

- **Render frame** (default): `SvEntities.Publish(manager, world)`. `SvStepSystem` steps once per rendered frame, first in `SimulationSystemGroup`.
- **Fixed step**: `SvEntities.Publish(manager, world, SvClock.FixedStep)` adds `SvFixedStep` to the handle entity. Then `SvFixedStepGroup` (last in `FixedStepSimulationSystemGroup`, so after tl) runs `SvOpenFrameSystem` (kills released slots, publishes `SvFrame`), `SvSendGroup` (systems that send into the open frame), `SvFixedStepSystem` (steps, republishes `SvFrame` with the frame's events) and `SvEventGroup` (systems that read the events). One fixed tick is one tl tick, then one sv step, the order `Outbox.Send` assumes in .NET. `SvStepSystem` skips a handle with `SvFixedStep`. When tl is in the project, `SvTimelineClockSystem` (`Sv.Unity.V4.Tl`) adds `SvFixedStep` to every handle once a `TimelineLibrary` exists.

`SvFrame` is unmanaged: `World` (a `WorldView` for `Lanes.Read`), `Sender` (the external `EffectWriter*`), `Events`/`EventCount` (the last step's `HostEvent`s), `Frame`, `LastDigest`. sv never references tl:

1. `SvOutboxSystem<TCell>` (Burst `ISystem`, in `com.sv.unity.v4`, in `SvSendGroup`) reads every `TCell : IComponentData, ISvOutboxCell` on an entity with `SvSlot`, turns each non-zero cell into the record `Outbox.Send` makes (source the slot, target from the aim lane holding slot + 1 or 0 for self, kind from the kind lane clamped to 0..255, `Origin.Timeline`) and zeroes the cell.
2. `SvTimelineRequestSystem` (Burst, in `Sv.Unity.V4.Tl`, compiled only with `com.tl.unity`, in `SvEventGroup`) reads the step's events and the `SvTimelineRule` buffer on the handle entity, and adds `TlRequests.Start`/`Stop` to the `DynamicBuffer<TimelineRequest>` of the entity whose `SvSlot` raised the event. tl applies them on the next tick, as `TimelineRequests.Apply` does in .NET.
3. `sv pack <folder> --glue tl --host unity` also writes `GlueEntities.g.cs`: per timeline channel a `partial struct XOut : ISvOutboxCell` (channel, kind and target lanes from the pack's `Kind` and `Target` intrinsics) and its `RegisterGenericSystemType(SvOutboxSystem<XOut>)`, plus `TimelineRules.AddTo(rules, findTimeline)`, one rule per event that starts a timeline. tl.unity's generator makes each `[TlState] XOut` an `IComponentData` and emits `TlKindSystem<TlAuto_<Assembly>_Jobs>`. Resolve timeline names once on the main thread: `TimelineRules.AddTo(SvTimelines.Rules(manager, handle), library.Find)`.
4. A tl player is an entity with `SvSlot`, `Playback`, `TimelineRequest`, `TimelinePlaying` (disabled), the `XOut` cells and each kind's `Types` (then `Init`).

Proof: `Sv.Unity.V4.TlEntitiesTests` builds a World in code (`TimelineKindTickSystem`, the generated `TlKindSystem`, the sv fixed-step systems, the two outbox systems and the request system) from `game.bytes`, gives every NorthStar3 slot a tl player entity and replays the five journals at 30, 60 and 144 rendered fps, at 1 and 11 job workers. Each fixed tick the cells tl wrote equal the journal's timeline sends, every digest equals the journal's (pins `A566FAEC8837BA57`, `2D6A06776AE25DCB`), sv steps exactly as many ticks as the journal has frames whatever the render rate, and the glue systems and every frame phase report Burst. `Sv.Unity.V4.Tests.SvClockTests` checks that each clock steps alone. The SubScene path (Timeline assets, a baked Playable Director) is not built yet.

tl glue: `sv pack <folder> --glue tl` and `docs/V3-HANDOFF.md` (M9). The old adapter v3 (`com.sv.unity`: `SvHost`, `SvLinkRegistry`, `SvJobs`) was deleted in M11; its history is in git and its issues are `issues/0127`, `0140`, `0142`.

## sv v4 columns in Entities and Burst (`com.sv.columns.entities`)

Add `com.sv.columns` and `com.sv.columns.entities` as `file:` packages; the second pulls Entities 7.0.0, Burst 2.0.0 and Collections 7.0.0.

1. Put `ColumnsWorldAuthoring` on one GameObject in a SubScene and wire the pack JSON `TextAsset`, capacity, writers, resolve parts (0 picks four per job thread), kernel and history (frames kept for rollback; 0 keeps none). Its baker compiles the pack (a broken pack fails the bake with its place) and bakes it into a `ColumnsPackBlob`.
2. Put `ColumnsEntityAuthoring` on each unit, wire the world authoring and pick the template and any lane values from the popups. The baker resolves the names to `ColumnsTemplate` and `ColumnsLaneValue`.
3. `ColumnsStepSystem` (`ISystem`, last in `SimulationSystemGroup`) builds the world from the config on its first update and publishes it on one entity: `ColumnsState` (unmanaged: `View`, `Sender`, `Sets`, frame, dropped, Burst probes) and `ColumnsHostHandle`. Every update it closes the last frame, despawns the slots of destroyed entities (and of entities whose `ColumnsTemplate` was removed) in ascending slot order, spawns new ones in entity order with their lane values, adds `ColumnsSlot` and `ColumnsSlotCleanup`, and schedules the next frame. Destroying the ECS world disposes the sv world.
4. Game systems send from Burst jobs: take `SystemAPI.GetSingleton<ColumnsState>().Sender` into an `IJobEntity` and call `Send(target, channel, amount, hits)` or `SendFrom(source, target, ...)`; a refused record counts in `Dropped`. Read lanes in later systems' jobs with `View.Get(slot, lane)`, `View.Event`, `View.IsAlive`. The step system writes `ColumnsState` and the readers read it, so Entities orders the jobs; on the main thread call `CompleteDependency()` on a `ColumnsState` query first.

5. Lane edits from systems: `ColumnsState.Sets.Set(slot, lane, value)` queues an edit; the step system applies the queue after it closes the frame and spawns, before the next frame (sorted by slot, lane and value, so of two edits to one lane the larger wins; dead slots and engine lanes are refused and counted in `ColumnsBurstHost.RefusedSets`).
6. Fixed step (for tl.unity, which ticks in `FixedStepSimulationSystemGroup`): tick `Fixed Step` on `ColumnsWorldAuthoring`, or add `ColumnsFixedStep` to the config entity. Then `ColumnsFixedStepSystem` steps once per fixed tick, last in that group after `ColumnsSendGroup`, and `ColumnsStepSystem` leaves the config alone. Two generic Burst systems in `ColumnsSendGroup` take tl's cells (any `IComponentData` on an entity with `ColumnsSlot`), cards first: `ColumnsCardSystem<TCell : IColumnsCardCell>` turns a non-zero `Level` into a `Sets` edit of the card's lane (`Card` names it; the card's timer channel ends it, so no records are sent), and `ColumnsOutboxSystem<TCell : IColumnsOutboxCell>` turns a non-zero `Amount` into `SendFrom(slot, target, channel, amount)` (target from the `TargetLane` holding slot + 1, or self). Both zero the cell; names resolve against the pack when the system starts. Register each with `RegisterGenericSystemType`. Generated cells for v4 packs are issue 0525.

Outside ECS, `ColumnsBurstHost(pack, capacity, writers, parts, kernel, history: h)` runs the same frame: `Schedule(dependsOn)`, `Complete()`, `Step()`, `Sender`, `View`, `World`.

Rollback runs on the Burst jobs too (spec section 9). With history above 0, records sent through `Sender` and the writers are logged per frame, and the host has `Inputs(frame)`, `Rewind(frame)` and `Resimulate()`; `Resimulate` replays the edited frames as the same two Burst jobs, resolving only the chunks an edit can reach. In ECS take the host with `ColumnsStepSystem.HostOf(entityManager, entity)` on the `ColumnsHostHandle` entity and call them on the main thread between updates. Resimulate before sending for the current frame (it throws otherwise). `Rewind` and edits that spawn or despawn can move slots, so the `ColumnsSlot` of an entity is only kept right if the same entities spawn in the same order again. The Arena sample (Package Manager > Samples) has a Burst attack system, a Burst health readout and their bakers.

Proof (the `sv Unity columns` job): the canon digest `77EC257ECB72B2CF` from the Burst host on both kernels and several writer and part counts, from records sent inside a Burst `IJobParallelFor`, a lockstep against `ColumnWorld.Step` under random traffic (strays, raw records, wide values, spawn and despawn), the ECS step system against a classic world frame by frame, baking, play mode in the default world, the canon late-input digest `143EFA56C94222D1` and a lockstep with a classic world through late inputs, rewinds and resimulates (partial and whole world), the ECS step system resimulating against a classic world, 0 B on warm Burst frames with and without history, and Burst probes at 1. `ColumnsClockTests`: each clock steps alone, lane edits apply between frames (and are logged as inputs for rollback), and card and outbox cells on the fixed clock give a hand-stepped `ColumnWorld`'s digest every tick at 30, 60 and 144 rendered fps. The bench prints `burst-rows` and `burst-scalar` beside the managed kernels for every shape.
